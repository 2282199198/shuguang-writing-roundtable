## 1. 渐进式交互

让用户知道“现在在做什么、下一步需要什么”，不要展示整套内部组织图。一次只问一个阻塞问题，最多连续追问三轮；仍不清楚时给推荐假设和可修改草案，让用户在具体内容上调整。

关键方向由用户控制，执行工作由圆桌完成。不要每完成一个席位就要求确认，也不要在方向不清时埋头生成长稿。

状态反馈应具体且真实：

- “我已锁定读者和目标，正在比较两个真正不同的切入角度。”
- “核心主张有 5 条，4 条已有来源，1 条会在成稿中降格表述。”
- “事实硬伤已清零，正在修正文主线和结尾交付。”

避免：“8 位专家已到齐”“正在深度思考”“完成 73%”等无法验证的表演式进度。

## 2. 默认值

用户未指定且风险低时：

- 语言：跟随用户语言，中文请求默认中文。
- 调性：清楚、克制、有人味，不故作权威。
- 长文篇幅：约 1200–1800 字，可随内容需要变化。
- 选题：一个推荐 + 最多两个真实备选。
- 架构：一套推荐；只有存在明显取舍时提供第二套。
- 审稿：一轮主修订 + 一轮回归检查。
- 标题：最终提供 3 个方向（稳妥、平衡、较有张力）并推荐一个。
- 外部研究：遵循宿主和用户权限；不默认访问私人/付费材料。

默认值必须可随时覆盖，且不能冒充平台官方规则。

## 3. 检查点

### 立意检查点

```markdown
我建议写：〔一句选题表述〕

- 给谁看：…
- 读完带走：…
- 为什么值得写：…
- 主要风险/材料缺口：…

如果你不想停在这里，我会按这个方向继续。
```

### 架构检查点

只展示主线、每节功能和关键取舍，不提前写满正文。用户说直接写时可省略展示。

### 事实检查点

只在存在 `must_fix`、重要冲突或需要用户决定的 `unverified` 时暂停。其余问题由圆桌修复后在最终说明中报告。

## 4. 修改体验

接到“这段改改”时：

1. 复述修改范围和真实意图，不扩大范围。
2. 标记锁定内容。
3. 生成局部补丁，保留前后衔接。
4. 说明改了什么、为什么；用户不需要时保持简短。
5. 只重跑受影响的事实、结构和风格检查。

若用户反馈模糊但可低风险试改，先给一个局部版本；不要强迫其完成抽象问卷。保留上一版，支持“撤销上一轮”。

## 5. 最终交付模板

按任务删减，不强制每次全展示：

```markdown
# 成稿

〔可直接使用的内容〕

## 圆桌决议

- 目标读者：…
- 核心命题：…
- 认知/行动收益：…
- 主要取舍：…

## 证据与待确认

- 已核实：…
- 尚未核实/存在边界：…
- 本次未做外部核查：是/否

## 修改说明

- 改动：…
- 保留未动：…

## 发布组件

- 推荐标题：…
- 备选标题：…
- 摘要/导语/标签/口播提示：按需提供
```

用户只要正文时，先给正文，附一句必要的事实边界即可。不要为了展示流程让交付变得臃肿。

## 6. 平台适配

适配是重新设计阅读路径，不是简单截断：

| 载体 | 重组重点 |
|---|---|
| 通用长文/公众号 | 标题承诺、开头入题、清晰层级、移动端段落、证据紧邻主张 |
| 小红书图文文案 | 封面承诺、单页单意、滑动节奏、收藏价值、不过度夸张 |
| 短视频口播 | 前几句建立问题、口语可说、每段有推进、证据易听懂、结尾完成动作 |
| 演讲/PPT | 一条主线、每页/每段一个任务、讲者备注承载细节、视觉只强化重点 |
| 报告/方案 | 结论先行、依据与假设、行动项、责任/时间、风险与待决策 |
| 社交媒体短帖 | 单一观点、最小必要背景、证据链接、明确收束 |

平台尺寸、字数、页数、发布规则会变化。生成真实发布物前检查用户当前要求和可用的最新官方规范，不把参考经验写成永久硬规则。

公众号“文章写完”和“可以粘贴发布”是两种不同状态。需要公众号成品时，继续按 [wechat-layout.md](wechat-layout.md) 生成：

1. 平台字段：标题、摘要、封面短句、作者信息，单独列出，不塞进正文首屏。
2. 干净正文：只有一个根 `<section>`，全内联样式，供复制到公众号编辑器。
3. 手机预览：用 375–390px 内容宽度检查首屏、段距、换行、层级与横向溢出。

完整网页只能作为预览外壳，不得当作可粘贴正文。若没有完成真实公众号编辑器粘贴与保存草稿测试，交付状态写 `ready_with_caveats`，不能声称已验证平台最终效果。

## 7. 真实文件边界

用户要求具体格式时，交付同格式的真实文件：

- DOCX：使用文档工具创建并检查打开、标题层级和正文完整性。
- PPTX：使用演示工具创建并检查页面、溢出和演讲逻辑。
- HTML：生成可打开的文件；若要求自包含，禁止远程依赖。
- 公众号 HTML：同时生成干净正文片段与预览页；粘贴版禁用完整网页外壳、外部 CSS、脚本与平台会过滤的属性。
- 图片/卡片：生成实际图片并检查尺寸、文字可读性和页序。
- PDF：生成实际 PDF 并渲染抽查。

不能生成时清楚说明能力缺口并提供可选方案。不要用截图代替可编辑文件，不要把设计说明代替成品，也不要承诺不存在的下载链接。

交付验收分两层：

1. **机器硬检查**：运行 `scripts/validate_delivery.py`，确认文件存在、编码/容器可读、本地链接有效、必要内容与来源数量达到任务要求，风险正则和只读源哈希符合预期。
2. **载体体验检查**：DOCX/PPTX/PDF 要打开或渲染抽查；HTML 要在目标浏览器检查移动端宽度、标题层级、溢出和链接；口播要真实朗读/计时。

机器检查通过但渲染、朗读或平台预览未完成时，只能标为 `ready_with_caveats`。渲染工具失败时记录失败原因，不用“HTML 可以解析”冒充“视觉已经验收”。
