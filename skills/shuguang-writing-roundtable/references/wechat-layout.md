# 微信公众号排版与交付契约

## 1. 这份规则解决什么

这份规则只在最终载体是微信公众号时加载。它不负责重写观点或补证据，而是把已经通过内容终审的文章变成：

1. 可直接复制进公众号编辑器的干净正文片段。
2. 可在本地浏览器查看的手机宽度预览页。
3. 与正文分离的平台标题、摘要、封面短句和作者字段。

公众号编辑器不是普通网页浏览器。能在浏览器打开，不等于粘贴后能保留样式。

## 2. 输入到输出

```text
终审 Markdown / 正文
        ↓
识别章节、金句、列表、引用、数据、来源
        ↓
选择一套主题并映射组件
        ↓
生成微信兼容的单根 section 片段
        ↓
生成手机宽度预览外壳
        ↓
机器校验 + 手机视觉检查 + 可选真实粘贴测试
```

标题、摘要和封面信息属于公众号后台字段。正文 HTML 默认不再重复放一个巨大的一级标题，否则首屏会只剩标题，读者还没接触文章价值就已经发生视觉疲劳。

## 2.1 公开终稿的来源处理

公众号公开终稿默认删去文末“参考资料 / 参考文献 / Sources / References”列表，但这不等于删除证据：

- 事实编辑继续维护内部证据台账、来源 URL、核验日期与未确认项。
- 公开正文可保留必要的来源身份，例如“国际劳工组织的研究显示”，但不在文末堆放链接清单。
- 用户明确要求公开来源、机构编辑规范要求披露、或医学/法律/金融等高风险内容需要来源透明时，才保留公开来源区，并在交付说明中写明例外原因。
- 不得为了去掉参考资料而删除正文中的限定条件、改强结论或伪装成无来源事实。

## 3. 干净正文的硬契约

公众号粘贴版必须满足：

- UTF-8 编码，文件内容从一个根 `<section>` 开始，并以对应的 `</section>` 结束。
- 只使用内联 `style`；不依赖外部 CSS、外部字体或运行时脚本。
- 禁止 `<html>`、`<head>`、`<body>`、`<style>`、`<script>`、`<link>`、`<div>`、`class`、`id`。
- 禁止 CSS 变量、`@media`、`@keyframes`、`display:grid`、`float` 和 `position:fixed/absolute/sticky`。
- 正文不使用 `<h1>`；平台标题在后台单独填写。
- 所有可见文字节点放进 `<span leaf="">...</span>`，避免复制后样式大面积丢失。
- 图片使用 `<img>`，但远程图片仍需在真实发布前确认已进入公众号可用图床；不得编造图片地址。
- 允许普通外链作为参考资料链接，但不能把“浏览器可点击”冒充“公众号已允许外链跳转”。

完整网页可以包含工具栏、复制按钮和脚本，但它只能作为预览外壳；被复制的目标必须仍然是上面的干净 `<section>`。

## 4. 手机阅读的默认视觉标尺

这些是本 Skill 的编辑默认值，不声称是微信永久官方规范：

| 项目 | 默认范围 | 目的 |
|---|---:|---|
| 预览内容宽度 | 375–390px | 按真实手机阅读判断换行与首屏 |
| 正文 | 15–16px，行高 1.75–1.9 | 保证密度与呼吸感 |
| 章节标题 | 19–22px | 清楚但不压过正文 |
| 小标题 | 15–17px | 建立第三层信息结构 |
| 段落下间距 | 16–22px | 让论证分段可扫读 |
| 章节间距 | 44–56px | 给大转折留出停顿 |
| 正文左右安全边距 | 10–16px | 避免贴边与过长行 |
| 高对比点睛 | 全文不超过 3 处 | 防止满篇都是重点 |

只保留三层视觉层级：章节、小标题、正文。引用、列表和提示块服务于信息类型，不能为了“显得排过版”而堆组件。每个段落尽量只完成一个功能；连续长段按论证动作拆开，而不是机械按字数截断。

## 5. 主题与组件路由

若宿主提供 `gzh-design`：

1. 先读其主题索引，再按题材与用户参考图选择一套主题。
2. 同一篇只用一套主题，不混搭。
3. 优先复用主题组件；不要重新手写一套看似相近但未经微信兼容处理的 CSS。
4. 深度分析、AI、教育观点、专业知识文，默认可选“石墨极简风”；教程、工具和高密度清单可选“摸鱼绿”。用户指定风格时以用户为准。
5. 排版阶段不得改变文章事实含义、删减来源限定或擅自增加作者经历。

若没有专门排版 Skill，则按本文件的硬契约生成朴素版：正文段落、两级标题、引用和列表即可；宁可克制，也不要为了装饰引入平台不兼容结构。

本 Skill 另外内置六套固定主题，见 [wechat-theme-pack.md](wechat-theme-pack.md) 和 `assets/wechat-themes/theme-catalog.json`。用户指定主题时直接采用；用户说“你决定”或未指定时，按内容类型自动路由。同一篇只使用一套主题。背景图片是可选增强层，正文结构不得依赖图片才能成立。

## 6. 五项视觉验收

在 375–390px 的手机宽度查看预览，并逐项回答：

1. **首屏**：是否能看到核心钩子或第一段价值，而不是被超大标题占满？
2. **节奏**：是否存在连续的大段文字墙、忽大忽小的字号或过松空白？
3. **层级**：不看全文时，章节标题和重点块能否让人理解文章推进？
4. **克制**：粗体、底色、边框、图标和强调色是否抢戏或彼此竞争？
5. **完整**：链接、引用、列表和图片占位是否在转换中遗漏；公开终稿的来源是否已转存内部证据台账？

还要检查横向溢出、长英文链接换行、表格在窄屏的可读性，以及正文最后一屏是否有明确收束。

## 7. 机器校验与状态

公开终稿先运行本 Skill 的硬校验：

```powershell
python -X utf8 scripts/validate_delivery.py "正文片段.html" --wechat-public-final --min-han 800
python -X utf8 scripts/validate_theme_catalog.py
```

若用户明确要求公开参考资料，改用 `--wechat-fragment`，并在交付报告记录原因。

若使用 `gzh-design`，再运行它的合规校验器；两者都通过，且完成手机预览后，可标记 `ready_with_caveats`。只有真实复制到公众号编辑器、保存草稿并复查样式后，才标记 `ready`。

机器检查不判断美感。视觉检查不证明平台粘贴兼容。两个检查都必须有，不能互相冒充。

## 8. 借鉴来源与采用边界

本规则只吸收公开项目的工作机制，不复制它们的主题代码或受保护素材：

- `doocs/md`：借鉴“Markdown 内容与主题渲染分离、即时预览、复制发布”的产品链路。
- `mdnice/markdown-nice`：借鉴“主题可替换、同一内容多平台适配”的思路。
- `sivan/heti`：借鉴中文排版要单独处理网格、混排、标点与移动端阅读的理念；公众号片段不能直接使用它依赖的外链 CSS 和脚本。
- `jiji262/wechat-publisher`：借鉴“全内联样式、主题配置、手机宽度主题预览、发布前测试门”的工程化做法。
