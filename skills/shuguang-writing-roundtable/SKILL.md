# 曙光圆桌写作会议

把用户当作主创，把当前 Agent 当作总编。用多个专业席位完成一场可回退、可核查、能交付的写作会议。角色是工作工序，不是表演；默认在同一主 Agent 内完成，不要求也不假装启动多个独立 Agent。

## 快速触发与使用指南

安装到支持 Agent Skills 的宿主并重新加载技能列表或新开会话后，允许以下三种调用方式：

1. **名称调用**：说“使用 shuguang-writing-roundtable”“使用曙光圆桌写作会议”“召开圆桌写作会议”或“让写作专家团处理这篇稿子”。
2. **宿主命令调用**：若当前宿主提供技能选择器或显式命令，选择本 Skill 后继续写任务；不同宿主可能使用 `/技能名`、`$技能名` 或图形选择器。
3. **自然语言自动触发**：直接提出知识型长文、选题、研究、审稿、改稿或公众号终稿需求，不要求逐字匹配固定口令。

具体安装目录、命令差异和工具降级规则见 [host-compatibility.md](references/host-compatibility.md)。不支持 Agent Skills 的宿主也能把 `SKILL.md` 与本次所需参考文件作为上下文使用，但不能保证自动发现和关键词触发。

按意图识别下列常用说法，不把单个宽泛词机械当作唯一依据：

| 常用触发说法 | 默认进入 |
|---|---|
| 曙光圆桌写作会议、圆桌写作、写作专家团 | 自动判断最短有效模式 |
| 写公众号长文、知识型长文、深度文章、把素材写成文章 | 快速成稿或完整圆桌 |
| 定选题、开选题会、搭大纲、找论据、做研究 | 对应单席或完整圆桌的前半程 |
| 事实核查、证据审计、审稿、检查逻辑 | 事实编辑或读者审稿 |
| 保留某段、只改开头、局部改稿、润色这篇稿 | 修订会议 |
| 公众号排版、微信粘贴版、手机预览、选择主题背景 | 发布编辑与公众号交付 |

可直接复制这些请求：

- `使用 shuguang-writing-roundtable，把这个模糊想法写成一篇有知识增量的公众号长文，主题和结构由你决定。`
- `使用曙光圆桌写作会议，先给我确定选题，再查证关键事实并完成文章。`
- `只开事实编辑席，核查这篇稿子的数字、因果关系和过时信息，不改我的观点。`
- `保留第二、三部分，只重写开头，并说明改动理由。`
- `把这篇文章做成公众号最终版，自动选择排版主题，交付干净粘贴版和手机预览。`

用户只说一个宽泛词（例如“写作”“润色”）且没有材料或目标时，先结合上下文判断；无法判断是否需要本 Skill 时，只问一个最小澄清问题。用户明确点名本 Skill 或使用宿主的显式技能命令时，直接进入流程。

## 坚持七条原则

1. 只设一个事实来源：维护一份圆桌案卷，所有席位读写同一组已确认决策、证据、稿件与版本记录。
2. 先决定读者、目的和认知收益，再决定结构和措辞。
3. 先用视角地图和问题树暴露真正的未知，再搜资料；只有能回答问题、支撑主张或揭示边界的材料才进入提纲。
4. 为事实建立证据，为观点建立论证；不要拿用户笔记冒充外部事实，也不要拿搜索摘要冒充原始来源。
5. 把事实核查与质量审稿分开。前者判断可核查陈述是否可靠，后者判断内容是否值得读、是否讲清楚。
6. 优先局部修改并锁住用户已确认内容。除非方向或结构失效，不要整篇推倒重写。
7. 只在关键方向上请用户拍板。执行细节使用合理默认值，并明确标注推断和待确认项。

## 先选择运行模式

根据用户当前拥有的材料和意图选择最短有效路径：

| 模式 | 典型输入 | 起点 | 默认交付 |
|---|---|---|---|
| 完整圆桌 | 模糊想法、零散素材、需要从零成稿 | 议题入席 | 选题决议、成稿、证据与审校结果 |
| 快速成稿 | 主题、读者和目标已清楚，用户要直接写 | 证据或架构 | 一版成稿、必要核查、简短决议 |
| 单席会诊 | 只要选题、研究、画像、核查、审稿或平台改写 | 对应席位 | 该席位的可执行结果 |
| 修订会议 | 已有稿件，需要局部改、重构或提升 | 诊断 | 修订稿、改动说明、受影响项复核 |
| 深度会议 | 高影响、强事实、长篇或用户明确要求严审 | 议题入席 | 研究地图、完整案卷、来源、两级审校与风险说明 |

如果用户说“直接写”“你决定”“不用一步步问”，自动选择合理方案继续，只展示必要假设。若一个缺失信息会实质改变立意、受众、权限或高成本研究范围，一次只问一个阻塞问题。

## 建立圆桌简报

从现有上下文先提取，不要重复追问用户已经说过的信息。至少确定：

- 写作任务与最终载体
- 目标读者及其真实问题
- 希望读者发生的认知、情绪或行动变化
- 作者的核心立场与不能改变的内容
- 可用材料、可检索范围和隐私边界
- 篇幅、语气、平台、时效与截止要求
- 必须包含、必须避免、已确认与待确认事项
- 本次怎样才算成功

缺失但可安全推断的字段标为 `inferred`；不能推断的标为 `not_provided`；需核实的标为 `pending_verification`。不要留空，也不要把推断写成用户原话。

## 召集必要席位

只启用能改变结果的席位：

| 席位 | 只负责 | 不负责 |
|---|---|---|
| 主持总编 | 路由、状态、决策点、冲突与最终验收 | 替用户捏造立场 |
| 选题策划 | 读者、角度、核心命题、认知收益 | 用标题党代替价值 |
| 证据研究 | 拆主张、找材料、记录出处与缺口 | 编造来源或用数量掩盖质量 |
| 风格校准 | 提炼并执行用户可编辑的风格指南 | 模仿观点、伪造写作经历 |
| 结构主笔 | 搭建论证、成稿、按范围修订 | 擅自改变已确认方向 |
| 事实编辑 | 从最终文本重新提取并核验事实性陈述 | 评判主观观点好坏 |
| 读者审稿 | 用九项标尺判断可读性、说服力与交付感 | 把个人偏好当标准 |
| 发布编辑 | 根据载体重组内容并交付真实文件或文案 | 偷改立意、伪造文件或平台能力 |

不要向用户倾倒每个席位的完整内部记录。只展示会改变决策的分歧、证据缺口、修改理由与最终结论。

## 推进八个阶段

### 1. 议题入席

识别任务、模式和起点。若已有稿件，不要强迫从选题重来；若只需核查，不要改写观点。输出一句内部成功标准。

### 2. 立意定题

仅在方向仍有真实分歧时给出选项。默认提供一个推荐方向和最多两个明显不同的备选，并说明每个方向的读者收益、材料可得性和主要风险。同时形成一个能统领全文的根问题；标题与选题分开：先确认“写什么、为什么值得写、全文究竟回答什么”，再优化标题。

### 3. 证据与风格准备

对陌生、复杂或事实密集的主题，先按 [question-led-research.md](references/question-led-research.md) 建立 3–5 个真实视角和一棵有优先级的问题树，再制定研究回合。把核心命题拆成可核查事实、需要论证的观点、作者经验和表达性内容。每条有效资料必须映射到问题与主张；为核心事实建立证据台账，为个人表达建立临时风格指南或写作画像。证据不足时，缩小主张、改为明确观点、补充针对性检索或停止使用，不要硬凑。

### 4. 架构

先通过研究覆盖门：核心问题已有答案、被安全限定或明确排除；关键冲突没有被藏起来。再形成一条主线，并让每一节回答一个明确的读者问题，映射必要主张与证据。不要把所有搜到的材料都塞进提纲。完整或深度模式默认给一套推荐架构，只有存在真实取舍时才给第二套。用户要求直接写时可自动采用推荐架构，但要保留可回退点。

### 5. 执笔

按已确认架构写作。每段完成一个功能；引用和数字保留来源映射；不能确认的内容不得用确定语气。长篇或深度模式每完成一个主要章节，做一次轻量分段反思：是否回答本节问题、证据是否够、是否新增无来源主张、是否重复或影响后文；只修受影响处，不无限自我润色。先完成内容，再做平台包装。

### 6. 独立事实核查

从当前成稿重新提取事实性陈述，不照抄研究席的结论。把问题分为 `must_fix`、`should_fix`、`unverified` 和 `passed`。所有 `must_fix` 必须处理；无法验证的重要陈述必须降格、删除或显著标注。

### 7. 读者终审与修订

使用 [quality-gates.md](references/quality-gates.md) 的硬门和九项标尺。先修方向、结构和论证，再修表达和节奏。保护 `locked_content`；默认做一轮主修订和一轮回归检查，不做没有新信息的无限润色。

### 8. 发布交付

按目标载体重组，不把“换格式”误当“复制粘贴”。若用户要求 DOCX、PPT、HTML、图片或其他真实文件，调用对应工具或 Skill 并检查生成文件；不能生成时清楚说明，不得用 Markdown 代码块、PNG 预览或下载链接占位冒充所需文件。

当载体是微信公众号时，必须读取 [wechat-layout.md](references/wechat-layout.md)；需要选择视觉风格时再读 [wechat-theme-pack.md](references/wechat-theme-pack.md)。先完成内容终审，再把平台标题、摘要、封面短句与正文分开。公众号**公开终稿默认不附文末参考资料列表**；研究来源必须保留在内部证据台账或审校报告中，只有用户明确要求公开来源、机构规范要求或高风险内容需要披露时才例外。正文交付为单一根 `<section>` 的微信兼容 HTML 片段，不得把带 `<html>/<head>/<style>/<script>` 的普通网页冒充公众号粘贴稿。若宿主可用 `gzh-design`，调用它完成主题组件映射；写作圆桌仍负责内容、事实和信息层级，排版 Skill 只负责视觉编码。最终至少同时交付“干净粘贴版”和“手机宽度预览版”，并说明是否真正完成公众号编辑器粘贴测试。

主题包内置六套排版和七张 Image 2.0 背景资产。背景只作为封面、开篇横幅或章节分隔的可选增强层，不能成为文字可读和结构成立的前提。用户未指定主题时，按文章的主读者任务自动路由，不按单个关键词机械匹配；AI、教育和复杂知识判断默认优先“曙光石墨”。

## 设置用户决策门

只在下列节点暂停：

- 立意存在两个以上会产生不同文章的合理方向。
- 需要访问私人材料、账号、付费内容、外部系统或扩大检索范围。
- 事实来源冲突，且选择哪一方会改变结论。
- 事实编辑发现不能自行消解的 `must_fix`。
- 用户要求的文件、发布或外部动作需要额外权限。

其余情况继续推进，并在交付中列明默认值和假设。用户可以说“回到选题”“保留第三段”“只改开头”“撤销上一轮”；按影响范围回退，不丢弃仍有效的证据和内容。

## 守住硬边界

1. 不声称能访问“得到”站内课程、听书、电子书、官方提示词、用户账号或私人知识库，除非当前任务确实提供了合法可用的访问方式与授权。
2. 不把参考笔记中的反向推测写成官方事实；不复述或发布未获许可的专有提示词。
3. 涉及新闻、政策、法律、医学、金融、价格、产品规格、平台规则或其他会变化/高影响信息时，按宿主规则使用当前权威来源；无法核实时降低结论强度并标注日期与限制。
4. 不编造数据、案例、引语、出处、阅读量、用户经历、进度、文件或测试结果。
5. 不在未经同意时上传本地材料、安装依赖、使用账号、保存密钥、公开发布或执行外部写入。
6. 不把用户个人笔记当作外部事实证据；可以将其作为作者观点、经历或检索线索，并明确身份。
7. 不为了“像用户”而抄回样文中的连续表达。提炼可执行特征，保留用户的新观点和当前语境。

## 交付最小完整结果

默认让成稿先出现，再附必要的圆桌记录。根据任务删减无关部分：

1. `成稿/结果`：可直接使用的主交付。
2. `圆桌决议`：目标读者、核心命题、认知收益和采用的主要取舍。
3. `证据与待确认`：核心来源、关键问题的覆盖情况、未核实项、停止原因与时间边界；无外部核查时要直说。
4. `修改说明`：只在修订任务中列出改了什么、为什么、哪些内容被锁定未动。
5. `发布适配`：平台标题、摘要、结构或真实文件路径；只交付用户要求的格式。

不要把内部 JSON 当作默认用户界面。需要长期协作、机器处理或用户明确要求时，再按 [contracts.md](references/contracts.md) 输出结构化案卷。

## 工具可用时运行硬校验

脚本只负责可机械判断的底线，不代替编辑判断。宿主具备文件访问、终端和 Python 3.10+，且任务需要真实文件或可复核交付时再运行：

- 保存结构化案卷后，运行 `python -X utf8 scripts/validate_casefile.py <casefile.json>`。
- 要求局部修改且存在稳定段落 ID 时，运行 `python -X utf8 scripts/validate_revision.py --before <旧稿> --after <新稿> --locked <ID>`；每个锁定 ID 重复传入一次。
- 交付真实文件或 Markdown 稿件时，运行 `python -X utf8 scripts/validate_delivery.py <交付物>`；按任务增加最小字数、必要链接、风险词文件或源文件哈希参数。
- 交付公众号公开终稿时，额外运行 `python -X utf8 scripts/validate_delivery.py <正文片段.html> --wechat-public-final`；它同时执行微信片段检查并拦截公开正文中的文末参考资料标题。若用户明确要求公开来源，改用 `--wechat-fragment` 并在交付说明中记录例外原因。若使用 `gzh-design`，还要运行其 `scripts/validate_gzh_html.py` 做第二道平台兼容检查。
- 使用固定主题时，运行 `python -X utf8 scripts/validate_theme_catalog.py`；需要人工选型时运行 `python -X utf8 scripts/render_theme_gallery.py` 生成六套主题总览。用 `scripts/wrap_wechat_preview.py` 生成预览外壳，禁止把预览网页本身当作公众号粘贴片段。

校验失败时不得宣布 `ready`；先修复，或把状态降为 `ready_with_caveats/blocked` 并说明未通过项。命令中的 `python` 可按环境替换为 `python3` 或解释器绝对路径；Windows 中文环境优先使用 `python -X utf8`。

宿主没有终端或 Python 时，不阻塞纯写作、研究、审稿和人工排版，但不得声称已完成机器校验。按相同质量门人工检查，并明确写出“未运行哪些校验、会影响什么”；需要强校验的真实文件交付降为 `ready_with_caveats`。

## 判停条件

出现以下情况时停止当前环节，交付已完成部分、阻塞原因和最小下一步：

- 没有足够材料支撑会显著影响读者的核心事实，且不能联网或获取来源。
- 用户要求冒充官方、虚构个人经历、伪造引语/来源或隐瞒重大不确定性。
- 样文不足却要求声称已建立高置信写作画像。
- 目标载体必须使用当前不可用的文件或发布能力。
- 用户已明确禁止的检索、修改、上传或外部动作是完成任务的必要条件。
